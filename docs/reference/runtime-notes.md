- `src/web/runtime_status.py` is imported by `src/runtime/pipeline.py` — do NOT delete it
- `heartbeat.txt` mtime is the canonical "is the trader process responsive" signal. Refreshed every `HEARTBEAT_INTERVAL_SECONDS` (default 60 s) from inside `src/main.py`'s sleep loop — so it fires between ticks too, not just at tick completion. A pipeline hang stops the heartbeat (the loop is on the main thread, no daemon) so liveness still reflects pipeline health. Thresholds derived from the same cadence: `< cadence × 3` → running, `< cadence × 10` → paused, else stopped. Helper at `src/runtime/heartbeat.py::heartbeat_label`. Prior history: 2 min threshold (way too tight for a 15-min tick) → 10 min in 2026-05-07 → 18 min (tick × 1.2) on 2026-05-08 → finally cadence-based with 60 s heartbeat the same day, after the tick-coupled basis kept under-counting healthy idleness.
- **External liveness watchdog (`ict-liveness-watchdog.{service,timer}`, 2026-05-11)** is the per-minute dead-man switch on top of the in-process heartbeat. Runs `scripts/check_heartbeat.py` every 60 s; Telegrams `[CRITICAL] Trader heartbeat stale` after 5 min of stale mtime; auto-restarts `ict-trader-live.service` after 8 min total stall (autoheal opt-in via `--auto-restart-after 3`, currently ON). **Restart-loop containment (`--max-restarts 5` / `--cooldown-min 3` / `--restart-startup-grace-seconds 180`, hardened 2026-06-09, BL-20260605-001):** restarts are capped per stall episode (then a one-shot `[CRITICAL] EXHAUSTED` ping + alert-only until the heartbeat recovers, which resets the budget), spaced by a cooldown, and skipped while the trader is inside its post-restart startup grace (so it's never killed mid-first-tick). A restart that fails to *dispatch* (e.g. `systemctl` timing out under CPU saturation — the 2026-06-09 incident, `BL-20260609-001`) does NOT consume an attempt or start the cooldown, so the watchdog retries next check instead of going silent. **Boot-grace (`--boot-grace-seconds 600`, added 2026-05-28):** for the first 10 min after a host boot the watchdog suppresses heartbeat missing/stale alerts AND autoheal (the trader is expected to be starting under systemd) and sends no "recovered" ping when it comes up — so a VM reboot no longer spams `[CRITICAL] heartbeat stale` + `[OK] recovered` on top of the reboot ping; a heartbeat still stale once the window closes alerts as a genuine failure-to-recover (uptime read from `/proc/uptime`, fail-open to "long up" so a real stall is never silently suppressed). Stdlib-only so it works even when the trader's venv is wedged. Full operator runbook: [`docs/runbooks/liveness-watchdog.md`](docs/runbooks/liveness-watchdog.md). Not to be confused with `ict-heartbeat.{service,timer}` which WAS the once-daily operator status digest at 13:00 UTC (`scripts/daily_heartbeat.py`) — **retired 2026-07-08** (notification streamlining): superseded by the hourly snapshot (`ict-hourly-snapshot.timer`, which now folds in a Training/ML section) + the once-an-hour consolidated prop pulse. `install_systemd_units.sh` actively disables the timer and never re-enables it; the unit files + script are kept inert for a trivial re-enable. **Note (2026-05-12 incident):** the watchdog correctly auto-restarted the trader after the 16h heartbeat-writer silent failure, but the new process retained whatever state was making bybit_2 dry. The Prime Directive (above) addresses the conceptual root cause: no auto-flip code paths should exist. The watchdog's restart behaviour is unchanged — restarting is fine; what was wrong was the flip itself.
- **IB Gateway auto-heal watchdog (`ict-ib-gateway-watchdog.{service,timer}`, 2026-05-28; reactive auto-restart re-armed 2026-06-22, BL-20260622-GATEWAY-MIDDAY-WEDGE)** — runs **on the gateway VM** (auto-enabled only where `/etc/ict-vm-role`==`gateway`; NOT on the trader). It probes `ib_paper` every ~5 min and, after 2 sustained-wedge checks, runs the local `scripts/ops/restart_ib_gateway.sh` `docker restart`. **History:** the reactive restart was disarmed 2026-06-10 (gateway-isolation redesign) in favour of one deterministic daily `docker restart` (`ict-ib-gateway-reset.timer`, 05:30 UTC) — because the reactive churn could starve the box the gateway then SHARED with the trader. That objection is moot now the gateway is isolated, and daily-only left a real gap: a MID-DAY wedge had no recovery until the next 05:30 (observed 2026-06-22 — an open MHG position tripped MONITOR BLIND; recovery needed a manual `vm-ib-gateway-recover`). So the bounded reactive guards are re-armed, with the daily reset kept as belt-and-suspenders. **2026-07-02 update (BL-20260623-002):** the daily reset was retimed 05:30 → **06:05 UTC** — 05:30 was actually *inside* IBKR's own documented ~03:45–05:45 UTC reset window, not after it, so the one deterministic restart the whole design relied on was racing the outage it existed to fix (confirmed recurring 2026-06-23 and 2026-07-02). The watchdog's `ExecStart` now also carries `--suppress-window-utc 03:45-05:45`: a wedge detected inside that window is still logged/alerted but never drives a restart (freezing, not resetting, the streak so it resumes the instant the window closes) — a restart attempted inside the window couldn't succeed anyway and was only burning the `--cooldown-min` budget the *next*, potentially-effective restart needed. The historical description below is kept as record. It is the MES dead-man switch for the *broker session* — distinct from the liveness watchdog above, which guards the *trader process*. Fired `scripts/check_ib_gateway.py` every 5 min (timer `OnBootSec=3min` / `OnUnitActiveSec=5min`); probes `ib_paper` via `ib_connect_check` — a logged-out Gateway still reports `connected=true` but `net_liquidation=None`, so **health = connected AND net_liquidation populated** — and after 2 consecutive wedged checks runs `scripts/ops/restart_ib_gateway.sh` (the same `docker restart` as the manual `vm-ib-gateway-recover` workflow). Guard rails `--restart-after 2 --max-restarts 3 --cooldown-min 20` mean a genuine IBKR lockout can never become a restart loop; once exhausted it alert-only escalates to Telegram. Heals the overnight IBKR-reset wedge that used to leave MES dark for hours pending a manual recover. Full runbook: [`docs/runbooks/ib-integration.md`](docs/runbooks/ib-integration.md) § Auto-heal watchdog; the root-cause investigation (IBC nightly auto-restart unreliable) is health-review backlog `BL-20260527-003`. Queryable on the diag surface (`/api/diag/services` + `/api/diag/journalctl?unit=ict-ib-gateway-watchdog.service`) since it was added to `_CANONICAL_UNITS` (#2192).
- **Naked-position auto-protect is unconditional baseline behaviour (no flag).** Each monitor tick `order_monitor._check_naked_positions` scans open live trades whose SL/TP is missing/non-positive, resolves the levels from the most recent matching order package (`_resolve_protective_levels`, direction + symbol-or-base-futures-root), and re-arms a broker-side GTC OCA bracket via `_attempt_naked_autoprotect` → `IBClient.place_protective`; the reconciler's adopt/re-attach paths do the same via `_rearm_broker_protection_after_recovery`. **Re-arm is IB-only on this DB-driven path**; non-IB accounts no-op here and the trade falls back to a one-shot naked-position alert. **The old rationale — "Bybit/OANDA/Alpaca attach SL/TP atomically at entry, so a naked orphan can't occur there" — is FALSE and was removed 2026-07-30.** A real-money `bybit_2` XRPUSDT position was observed live with no bracket at all (BL-20260729-BYBIT-NAKED-POSITION-BLINDSPOT), and under `BYBIT_TPSL_MODE=partial` the qty-scoped legs desync from the netted one-way position (an `intent_reduce` adds none; a close cancels its own trade's legs; the 20-leg cap can block an amend). Bybit is covered by its own broker-state sweep below. A live position with no stop is an unacceptable state the system must always correct — there is **no enable gate** (Prime Directive: no default-off flag in front of a required capability). The earlier `NAKED_POSITION_AUTOPROTECT` toggle was removed 2026-06-15 (BL-20260615-MGCNAKED); a leftover value in `.env` is ignored.
  - **Broker-side VERIFICATION (not just journal-driven), all three venues:** the DB-driven `_check_naked_positions` above only flags a row whose *journal* SL/TP is missing — a position whose broker bracket was silently dropped (cancelled at the RTH close for Alpaca day-TIF legs; never-placed / breaker-flap-dropped for IB) keeps its journal SL/TP and slips past it. Three broker-state sweeps close that gap by asking the broker whether a **resting protective leg actually exists** and re-arming when none does: **Alpaca** — `_check_broker_naked_equity_positions` → `AlpacaClient.has_protective_orders` (cheap HTTP, every tick; BL-20260629-ALPACA-NAKED-BRACKET); **IB** — `_check_broker_naked_ib_positions` → `IBClient.protection_coverage` (an **account-wide `reqAllOpenOrders`** read — IB order visibility is per-client-session, so `openTrades()` alone would false-read naked — **cadence-gated** via `IB_BROKER_NAKED_CHECK_SECONDS` default 300s to stay clear of the IB pacing wedge class; BL-20260709-IB-BROKER-PROTECTION-UNVERIFIED, the 2026-07-09 MGC monitor-blind incident). ⚠️ **IB protection is a QUANTITY AND TWO-SIDED** (2026-08-16, `BL-20260816-COVERAGE-IS-ONE-SIDED`) — *(this bullet previously named `IBClient.has_protective_orders` here, contradicting the `/api/diag/ib_open_orders` row in this same file, which correctly distinguishes the boolean from the coverage read; the sweep body calls `protection_coverage`)*. `protection_coverage` classifies each resting leg through `_protective_leg_side` and returns **`stop_qty` and `target_qty` separately** beside the back-compat `covered_qty`. It used to grade both sides with ONE membership test (`"STP" in t or "LMT" in t or "TRAIL" in t`), so a stop and a take-profit counted as interchangeable and a stop-only position reported fully covered — measured 2026-08-16 on `ib_paper`: MGC 105 long and MES 15 long each held a stop, **zero limit orders existed account-wide**, and nothing had ever alerted. Note `"STP LMT"` contains `"LMT"`, so the classifier tests the stop family FIRST — a naive LMT-first test would file every stop-limit as a take-profit and *manufacture* target coverage, which is strictly worse than the bug it replaces. `IBClient.has_protective_orders` still exists and legitimately keeps the combined test (it answers "does ANY protective leg rest?"); its docstring forbids naked-detection use and routes callers here. The target side **alerts, deliberately without re-arming**: a missing stop is a safety gap to close blind, a missing take-profit is decision-time geometry (`trades.take_profit_1`) that a repair must read rather than invent — see the `attach-ib-target` action. **Bybit** — `_check_broker_naked_bybit_positions` → `_bybit_position_protection` (every tick, unconditional; BL-20260729-BYBIT-NAKED-POSITION-BLINDSPOT). Protection here is a **QUANTITY, not a boolean** (PR #8000, 2026-07-30): a netted position is ONE exchange position holding N journal trades and N qty-scoped legs, and a Partial leg's `slSize` covers only its own qty — so `covered_qty` is summed and compared to `size`. `covered == 0` → Full-mode re-arm; `0 < covered < size` → **partially naked**, topped up with a qty-scoped Partial SL leg for exactly the uncovered qty via `execute.modify_open_order`; an unparseable leg qty makes coverage ungradeable and the re-arm is **skipped rather than guessed** (a blind Full re-arm would stamp one trade's stop over the whole netted position). It also emits two **detect-only** signals, both live-verified firing on 2026-07-30: `over_covered` (SL legs > 1.5x the position — leg over-accumulation, `BL-20260730-BYBIT1-XRP-LEG-OVERACCUM-WORSENING`) and `journal_qty_divergent` (open journal rows summing above the netted exchange size ⇒ a phantom row). Neither is remediated here — detection only. ⚠️ **`over_covered` NOW PAGES THE OPERATOR, AND UNTIL 2026-08-26 IT DID NOT** (`_emit_bybit_over_cover_alert`) — the exact defect fixed for IB one day earlier and explicitly left unchecked here: `logger.error` reaches the systemd journal and **nothing else**, never `outcomes.jsonl`, which is what feeds Telegram, `/api/bot/notifications` and `/api/bot/logs?level=error`. Measured over the 401-row operator ERROR+ feed spanning 2026-08-20T09:42Z–2026-08-26T00:33Z: **zero** Bybit rows against **three** `ib_stop_over_cover` rows in the same feed — a POSITIVE CONTROL, so the silence is this page's absence and not an empty feed, while the trader's own symbol-scoped read had `bybit_1`/ETHUSDT at **167% over-covered**. ⚠️ **It is deliberately NOT `_emit_stop_over_cover_alert(venue="bybit")`**: that page's whole hazard argument is IB-specific and would be FALSE here — it warns of a disjoint OCA group selling again into a **naked SHORT** and routes to `cancel-ib-order` over IB's clientId cancel-rights rule (Error 10147), whereas Bybit has no OCA groups and every resting SL leg is `reduceOnly` (measured on all four live `bybit_1` symbols), so it cannot flip the position. The Bybit hazard is (1) the **20-leg cap**, at which `set_trading_stop` refuses (110061) and a genuine protective tightening fails SILENTLY — hence the leg count and cap headroom on the page — and (2) a reduce-only leg owned by a **CLOSED** row cutting a live position at a dead trade's level. ⚠️ **THE PAGE'S HEADLINE NAMED A CAUSE NO CODE PATH TESTED UNTIL 2026-09-02, and it is the `covered_qty` sum that is at fault, not the wording.** `_bybit_position_protection` sums **every** resting Partial SL leg on the symbol with **no reference to the leg's side**, and the page then described that side-blind total as coverage OF THE GRADED POSITION. Harmless while every symbol was one-way netting; **not harmless since HEDGE mode was armed on `bybit_1`/`bybit_2` (2026-08-30, `BYBIT_HEDGE_MODE_SYMBOLS`)**, because one symbol can then carry legs for TWO books and they land in one sum. MEASURED on `bybit_1`/BTCUSDT (`/api/diag/bybit_open_orders`, read 2026-09-02T03:30:33Z, trader `git_sha 68e73de8`): the live position was `Buy 0.018 positionIdx=1` and its own legs were `Sell 0.018` SL + `Sell 0.018` TP — **an exact 1.00× match, not over-protected at all** — while the entire excess was `Buy 0.46` SL + `Buy 0.46` TP, reduce-only orders that can only reduce a SHORT. The page read *"position 0.018 but resting SL legs total 0.478 (2656%)"*. That is UNPROVENANCED DIAGNOSTIC OUTPUT sub-class A, and the remedy per this file is to **branch on the actual condition, not reword the label**: `src/runtime/bybit_leg_sides.py` (a pure function, so the policy is arguable in tests rather than against a live position) splits the legs into four never-collapsed classes — `reduces_graded_book` · `reduces_other_book` · `leg_side_unreadable` · `position_side_unreadable`, the last two both *we did not look* — beside a three-state `other_book_state` (`impossible_one_way` / `possible_hedge` / **`unknown`**). ⚠️ **The page still does NOT say "orphaned"**: under one-way netting an other-book leg is stranded by construction, but under hedge mode it may be a LIVE sibling's protection, and calling it orphaned would invite cancelling a live position's stop. ⚠️ **THE TRIGGER STAYS SIDE-BLIND AND `covered_qty` IS UNCHANGED** — the sum is the UNION of both conditions, so narrowing the trigger would make the other-book case go SILENT, and re-pointing `covered_qty` would change which positions get RE-ARMED (Tier-2). Only what the page SAYS moved. ⚠️ **The sibling defect — the re-arm decision reading the side-blind sum, so an other-book leg can push `covered_qty` past `size` on a position whose own stop is gone and `if covered + eps >= size: continue` skips a genuinely naked book — is now FIXABLE PER ACCOUNT, and this row said it was *still OPEN and deliberately not fixed* until 2026-09-02. Do not re-quote that.** The re-arm/top-up comparison can read `bybit_leg_sides.graded_book_coverage` instead, gated by `BYBIT_GRADED_COVERAGE_MODE` / `BYBIT_GRADED_COVERAGE_ACCOUNTS` (see that row). ⚠️ **BUT THE SHIPPED ALLOWLIST IS EMPTY, WHICH FOR THAT KNOB MEANS NONE, SO THE DEFECT IS LIVE ON EVERY ACCOUNT UNTIL THE OPERATOR ARMS ONE** — operator Tier-2 decision 2026-09-02 was to stage on `bybit_1` (demo) first, explicitly accepting that `bybit_2` (REAL MONEY) stays exposed during the soak and that demo may never produce the triggering collision. Read the live arm with `get-env` against `/proc/<MainPID>/environ`; both keys are needed, since `apply` with an empty allowlist binds nothing. `covered_qty` itself is unchanged and stays side-blind — it feeds the over-cover TRIP, which is the union of two conditions. **Level is `ERROR`, not `CRITICAL`**, deliberately: both reach Telegram (`_TELEGRAM_LEVELS` = {ERROR, CRITICAL}) so nothing is lost in delivery, and CRITICAL is reserved for a position that is UNPROTECTED or REVERSED — spending it on an over-protected reduce-only book is how the channel gets trained away (202 of 376 CRITICALs were once one un-latched alarm). Severity is the **leg count**, so a worsening breaks the 6h window; the cooldown is the **shared** `_cooldown_admits`, never a copy. All three are fail-safe: a `None`/could-not-confirm read is skipped (never re-arm on an unconfirmed broker read), and the broker's own order state IS the idempotency (an already-protected position is never re-armed, so no OCA/OCO stacking).
