## Critical finding

| id | claim (short) | pipeline |

| `m21-entry-sweep-inert-fold-inflation` | `m21_entry_sweep.py`'s walk-forward gate counts a fold as a win whenever the lever merely **ties** the baseline (fired zero times that year), with no way to tell a genuine improvement from a no-op fold — the same bug class already filed and partially fixed elsewhere (`BL-20260817-FLEET-SWEEP-WF-COUNTS-INERT-FOLDS-AS-WINS`) but reimplemented here with none of that fix. `config/strategies.yaml` cites this exact tool's WF fraction ("wf 5/6", "wf 4/6") as shipped evidence for entry-filter levers now running `execution: live` on real-money `bybit_2` legs (`trend_donchian_xrp_4h`, `ada_pullback_2h`). | `PI-20260927-ZGQPHR3D-0001` |

I re-read `m21_entry_sweep.py:190-213` directly: `ok = (fc["net_total_r"] >= fb["net_total_r"] and fc["max_drawdown_r"] <= fb["max_drawdown_r"])`, `wins += 1 if ok else 0`, verdict `PASS` at `wins*3 >= usable*2` (≥2/3). A fold where the cell's metrics are byte-identical to baseline (the lever fired zero times) satisfies `>=`/`<=` trivially and is counted as a full win — indistinguishable in the printed `wins/usable` fraction from a fold where the lever genuinely helped. Confirmed the live citations myself: `config/strategies.yaml` around the `trend_donchian_xrp_4h` and `ada_pullback_2h` M21 E-2 entries carries `execution: live` and cites this exact WF fraction as evidence. This is rated **critical rather than high** because, unlike the sibling high finding below, it has a *confirmed, current, real-money* citation trail: the fraction being read today by anyone reading those config comments as evidence may be inflated by an unknown, unmeasured number of inert folds, and there is presently no way to tell.

## `prop_ev_sim.py` — the special-focus file (1250 lines, read in full)

Per the dispatch's explicit instruction, this file — the harness the operator's prop-account roster decision rests on — got the closest read in the audit. **Overall: sound.** I independently re-ran `--book breakout_1` end-to-end and it matched the committed evidence record (`research/results/_unattributed/b6-prop-ev-breakout_1-20260927.jsonl`) byte-for-byte across all four mark modes, confirming genuine determinism rather than a stale/cached artifact. Point by point against the dispatch's five questions:

- **(a) Breach/drawdown termination:** correctly modeled as a first-class death cause (`Life.died`/`death_cause`); a life that breaches early with zero payouts nets to `-fee`, never a phantom positive.
- **(b) Costs:** never defaulted to 0 and treated as measured — `CostConfig` ships Breakout's own real commission/slippage/swap figures, and the ruleset loader **refuses** (raises) rather than silently mis-modeling a changed YAML.
- **(c) Look-ahead:** none found — the block bootstrap redraws whole calendar blocks (not naive per-trade resampling), intra-trade calibration uses only each trade's own already-known MFE, and a staleness gate refuses to score a leg whose evidence record's config fingerprint no longer matches the strategy's *current* live params.
- **(d) Population/denominator:** internally consistent in the simulation itself, but the **committed E5 record's population description is mislabeled** (see medium finding below) — a real but narrow issue that doesn't change the underlying EV/CI number or verdict.
- **(e) Silent except/fallback:** none in the simulation path; `grade()`/`grade_v2()` fail closed to `"indeterminate"`, never a false `"pass"`.

Two **medium** findings attach to this file, both peripheral to the core simulation:
- `prop-ev-sim-population-description-mismatch`: the committed E5 record's `population.description` says *"n = total trades in the resampled history"* but the numeric `n=234` is actually the raw pooled historical OOS trade count fed **into** the resampler, not the resampled stream itself (~63,600 for path mode). Verified directly against the committed record and the code (`n=len(trades)`).
- `prop-ev-sim-room-frac-default-drift`: the `--room-frac` CLI default (`0.45`) has drifted out of sync with the operator-decided `k=0.33` now in `config/prop_rulesets/breakout.yaml` and the live executor `src/prop/prop_sizing.py`. Confirmed both live values are `0.33` against the tool's hardcoded `0.45`. The one committed run used `--sizing balance`, so it is unaffected — this is a trap for a future unflagged `--sizing room` run.
