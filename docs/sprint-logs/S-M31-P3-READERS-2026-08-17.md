## Work Completed

### The read half lives in the module that owns the table

`enrich_record` / `read_records` / `telemetry_by_trade_id` were added to
`src/runtime/position_telemetry.py` rather than to either router. **One owner
for "what does a telemetry row MEAN"** — the diag surface and `/positions`
resolve through the same function and cannot drift into two answers, which is
the `_regime_score_semantics.py` lesson (two probes re-derived a definition
independently and both got it wrong on the same day).

They add the three things **the table cannot say**:

1. **`lifecycle`** — is this row FINAL? Four states, never collapsed: `open` ·
   `closed` · `unknown_no_trade_id` (the package never filled) ·
   `unknown_trade_absent` (a trade id `trades` does not have). It is a **LEFT**
   join deliberately: an inner join would DROP the unattributable row and make
   it look like a row that does not exist.
2. **`peak_pct_of_cap`** — how close the trade EVER got to its venue ceiling.
   The stored `pct_of_cap` is computed from `open_r` (where it is NOW). Both are
   correct for what they name; only this one answers the P4 Check-A question.
3. **`arm_reach`** — is this row's declared arm reachable under this row's OWN
   ceiling? `reachable` · `unreachable` · `no_arm_declared` · `unmeasured`.

Plus `peak_r_is_lower_bound: true` stamped on **every** row, including closed
ones — the last write precedes the close by up to one exit pass, and a bar
extreme cannot see an intrabar excursion.

### Reader 1 — `GET /api/diag/position_telemetry`

Not a second copy of `/api/bot/db/table/position_telemetry`, which already dumps
the rows. This serves the enriched view plus a summary (`by_lifecycle`,
`by_arm_reach`, `peak_above_cap`, `final_rows`). `present: false` distinguishes
"table not created" from "table empty" — the collapse `/api/diag/journal` was
fixed to stop making.

### Reader 2 — the `r` block on `/api/bot/positions`

Joined **by `trade_id`**, which the route already holds as `r[0]`, so the
existing positional-index SQL was **not touched at all** — zero risk to a live
consumer route. `null` when a leg writes no telemetry (only the
donchian/pullback monitors do): absent, never a zeroed block, because zeros
would assert a measured flat trade.

**One telemetry read per RESPONSE, not per row.** A per-row query would be an
N+1 on the same blocking sqlite path the route's `asyncio.to_thread` offload
exists to keep off the event loop.

Replayed against the live 14-row payload:

```

by_arm_reach {no_arm_declared: 11, unreachable: 2, reachable: 1}

xrp_pullback_2h        open    peak/cap 87.12%   arm 4.49  UNREACHABLE
ada_pullback_2h        open    peak/cap 73.31%   —
trend_donchian_ada_4h  open    peak/cap 60.64%   —
```

It finds, without being told: the same 13/1 lifecycle split, the same zero
ceiling breaches, and **2 of 3 declared arms unreachable** (`xrp_pullback_2h`
4.49 vs cap 3.9233; `qqq_trend_long_1d` 3.56 vs cap 2.1258) — findings that
previously took a hand audit and four diag pulls.

### P5 — proposed, NOT shipped

`docs/design/m31-p5-telemetry-reading-lever-PROPOSAL.md`. P5 is *"any lever that
READS telemetry to change an exit"*, **Tier-3**, gated on *"the same backtest
gate as every other lever"*. **That gate is measured NOT MET:**

| measurement | population | consequence for P5 |
|---|---|---|
| P4 Check B **abstains** | n=**1** final live row, fleet-wide | no established backtest↔live MFE parity |
| M20 levers fired **13 times ever** | vs 1,142 closed trades | the live journal cannot grade an exit lever |
| harness per-trade `mfe_r` **committed nowhere** | key census, all 1,376 corpus rows | the backtest half has no standing artifact |

A P5 lever shipped today would be tuned on a harness whose agreement with the
live book **has never been checked** — the exact defect family M31 exists to
close. Shipping it would spend the milestone's own result.

The candidate is **named** so it is not re-derived: an **`rr_from_here` floor**
(the milestone's own motivating question — 0.71 on the XRP trade, i.e. holding
for the target risks more than it stands to make), with **five falsifiable
preconditions** and an explicit note that a `peak_r`-driven giveback lever is
deliberately NOT first, because swapping an existing lever's input to a stored
lower bound would make it fire late by an unquantified amount while looking like
a refactor.

## Contradictions or Drift Found

**1. None new in the code read this session.** The two structural defects P4
surfaced (`PB-20260817-TELEMETRY-HAS-NO-TERMINAL-SNAPSHOT`,
`PB-20260817-NO-COMMITTED-PER-TRADE-HARNESS-MFE`) remain open and are now
*mitigated on the read side* rather than resolved — the join gives a consumer
finality, but a **lever** must not depend on a join to know whether the trade it
acts on is still live. That distinction is why P5 lists the terminal writer as
precondition 1.

**2. A reader is not a fix for a collapsed state, and this log should not be
read as claiming it is.** `lifecycle` is derived, not stored. If a future
consumer reads `position_telemetry` directly — as the Data Explorer does — it
still sees a closed row that looks open. The durable fix stays Tier-2.

## Risks and Follow-Ups

- **P5 stays withheld** until its five preconditions hold. Precondition 2 is the
  binding one and is a data problem, not a work problem.
- **The new readers are themselves now subject to §8's signal.** If
  `/api/diag/position_telemetry` and the `r` block accrue a month with nothing
  consuming *them*, that is the same failure one level up. The nearest real
  consumer is the exit-ladder input (M31 P3's fourth bullet), still unbuilt.
- **Not shipped from P3's own list:** the position-lifecycle **banner kind** on
  `/api/bot/notifications` and the **exit-ladder input**. The banner is cheap
  and additive; the ladder input sits closer to P5 and should wait behind the
  same gate.
