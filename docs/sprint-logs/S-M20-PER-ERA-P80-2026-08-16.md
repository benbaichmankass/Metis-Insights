## What the verification showed that I could not have asserted beforehand

- **`trend_donchian`'s per-year p80 swings 3.87 -> 6.35 across five years** — a
  64% spread, every year `computed` at n=11-28. That is this sprint's whole
  premise measured on one leg: the pooled 5.5R describes no regime in particular.
- **`gld_pullback_1d` came back 11/11 `thin`** (n = 1-6 per year). The floor
  refusing a percentile on any single year of a 1d equity leg while the widening
  window still answers at n=10 — the two halves of the design doing separate jobs.
- **A PREDICTION I GOT WRONG.** I predicted gld's recent-era span would be
  2023-2025; it is **2017-2020**. `resolve_split` gives that leg a PER-LEG split
  of `2020-03-03` while my probe had used the default `2025-07-01`, so IS ends in
  2020 and the newest year *within IS* is 2020.

  This is the design decision I would most have liked to get wrong and did not:
  the field is stamped `era_basis: calendar_year_within_IS` and publishes its
  span, so the artifact states its population. Had it been labelled plain
  `recent_era_p80`, this row would read as a claim about 2023-2025 that it does
  not make — and nobody would have caught it, because the number is perfectly
  real. A correct number under a label naming the wrong population is exactly
  sub-class **A** of the diagnostic-provenance rule.

## Deferred Items
- The capped-vs-uncapped populations are **different books** (the cap acts as a
  take-profit and banks winners that would otherwise round-trip), so the
  "−15% to −71%" cap effect is not the same trades re-measured. A per-trade
  matched comparison is possible but was not run.
- `by_era` reports calendar years only. Clustering them into the regime eras
  the row names (2010-2013 / 2014-2019 / 2020 / 2022-2024 / 2025-2026) is left
  to the reader, deliberately.
- **`BL-20260814-TP-GEOMETRY-RECORDED-ON-2-PERCENT-OF-CELLS-SO-ABSENCE-CANNOT-MEAN-ANYTHING`
  is 17x stale, and
  I did not fix it.** Measured this session: `tp_geometry` is recorded on
  **170/416 = 40.9%** of matrix cells against the row's `10/416 = 2.4%` — the
  same denominator, so directly comparable. Its criteria (1)/(2) genuinely
  remain open (`tp_geometry` is defined in neither the matrix's `_doc` nor its
  `legend`), so the row is right to stay open; but a reader acting on "2.4%"
  would badly misjudge how much work is left.

  Recorded so the next session need not re-derive it: **both consumers tolerate
  a stamped `"unrecorded"`.** `m20_coverage_rollup`'s stale-grader branches on
  `geom == GEOMETRY_NO_TP` / `== GEOMETRY_LIVE_PARITY` and otherwise falls to an
  `else` that grades by the date proxy, so a stamped string lands in the same
  branch as `None`; and `geometry_coverage` counts
  `counts["unrecorded" if geom is None else str(geom)]`, whose null-bucket
  literal is *already* the string `"unrecorded"` — so stamping merges into that
  bucket rather than falsely reporting 100% coverage. I checked this because the
  obvious risk of stamping is that it silently satisfies the metric that exists
  to measure the gap; it does not.
